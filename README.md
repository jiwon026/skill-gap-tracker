# Skill Gap Tracker

채용공고를 매일 자동으로 모아 **요구 스킬과 내 스킬·경험을 대조**하고 지원 우선순위와 자소서에 쓸 어필 포인트까지 붙여 Notion에 적재하는 파이프라인.

신입 데이터 분석 직무를 준비하면서 "이 공고에 지원할 수 있나, 무엇이 부족한가, 무엇으로 어필할까"를 공고마다 손으로 확인하던 일을 자동화했다. 실제로 매일 돌려 쓰는 도구다.

## 무엇을 하나

```
수집 → 스냅샷 → 추출 → 분석 → Notion
```

| 단계 | 하는 일 |
|---|---|
| 수집 `collect/` | 소스별 응답을 공통 레코드(`Posting`)로 옮긴다. 소스 차이는 이 경계 안에서 흡수한다 |
| 스냅샷 `store/` | 필터 **이전**의 원본을 날짜별 JSONL로 남긴다. 판정 규칙을 고치면 과거 데이터로 다시 계산할 수 있다 |
| 추출 `extract/` | 직군·경력·지역 판정, 회사 공통 문구(상용구) 제거, 요구 스킬·어필 경험 추출 |
| 분석 `analyze/` | 보유/부족 스킬, 지원 우선순위 |
| 적재 `report/` | Notion DB에 upsert. 사용자가 고친 '상태' 열은 절대 덮어쓰지 않는다 |

Notion에는 공고마다 이런 행이 생긴다.

| 열 | 내용 |
|---|---|
| 우선순위 | 높음·중간·낮음. 어필할 프로젝트 수로 정하고 지원 대상 회사가 아니면 한 단계 내린다 |
| 보유 / 부족 스킬 | 공고가 요구하는 스킬을 보유 여부로 나눈 것 |
| 어필 경험 · 어필 포인트 | 공고 문구와 맞닿는 내 경험과, 자소서 첫 문장으로 쓸 한 줄 |
| 규모 | 대기업·중견·중소·스타트업 |
| 공고 현황 | 모집중 · 제외됨 · 마감. 행을 지우지 않고 상태만 바꾼다 |
| 마감 | 날짜 또는 '상시채용' 등 |

## 설계에서 신경 쓴 것

실제 데이터를 돌리며 틀린 결과를 보고 고친 것들이다. 자세한 근거는 각 모듈 docstring과 테스트에 있다.

- **판정 순서가 결과를 바꾼다.** 회사 공통 문구인지를 직군 필터 뒤에 판정하면 회사당 표본이 2건으로 줄어 실제 자격요건까지 '반복 문구'로 지워졌다(요구 스킬 0개). 판정은 필터 이전 전체 공고로 하고 지역·트랙만 바꿔 여러 번 올린 공고는 하나로 묶은 뒤 센다.
- **경력은 숫자 > 제목 표기 > 본문 자격요건 순으로 본다.** 경력을 숫자로 주지 않는 소스에서 2~5년 경력직이 신입 목록에 섞였다. 본문의 필수 자격 섹션만 읽고, 우대 사항의 연차는 무시한다.
- **'모름'과 '해당 없음'을 구분한다.** 마감일이 비어 있으면 상시채용이 아니라 '모름'이다. 본문이 없는 소스는 표식을 심어 스킬이 0개인 이유가 '요구가 없어서'인지 '읽을 본문이 없어서'인지 데이터만 보고 알 수 있게 했다.
- **목록이 전체인 소스에서만 마감을 판정한다.** 키워드 검색 소스에서 '목록에 없음'을 마감으로 읽으면 검색 결과에서 밀려난 공고가 전부 마감으로 찍힌다. 수집이 실패했거나 0건인 날도 판정하지 않는다.
- **근거 없는 정밀도를 만들지 않는다.** 스킬 보유는 이진 판정이고 '매칭 스킬 몇 개부터 높음' 같은 임계값을 두지 않는다. 사원수로 중견·대기업을 추정하지 않는다.

## 데이터 소스

공개 저장소의 수집기는 인증 없이 공개된 채용 API와 공식 오픈 API만 쓴다. 요청 사이에 1초를 두고 하루 한 번 받아 캐시한다.

| 소스 | 비고 |
|---|---|
| 우아한형제들 채용 API | 목록 + 공고별 상세 |
| 사람인 오픈 API | `SARAMIN_ACCESS_KEY` 필요. 본문을 주지 않아 본문 대신 키워드·직무코드를 쓴다 |
| Greenhouse Job Board API | 코드는 있으나 현재 `sources.yaml`에서 꺼 두었다 |

그 밖의 개인용 수집기는 `collect/local/`에 두면 `run.py`가 자동으로 붙인다. 이 폴더는 저장소에 포함하지 않는다.

> 사람인 데이터를 쓴 결과물에는 **Powered by 취업 사람인** 출처 표기가 필요하다.

## 실행

Python 3.14 기준. 모든 명령은 저장소 루트에서 실행한다.

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # macOS·Linux: .venv/bin/python
```

개인 설정 세 개는 저장소에 없고 같은 형식의 예시만 있다. 복사해서 본인 내용으로 채운다. 채우지 않으면 예시 파일로 돈다.

```bash
cp config/profile.example.yaml    config/profile.yaml      # 보유 도구
cp config/experience.example.yaml config/experience.yaml   # 프로젝트 경험 · 어필 문구
cp config/companies.example.yaml  config/companies.yaml    # 지원 대상 회사
```

| 환경변수 | 없으면 |
|---|---|
| `NOTION_TOKEN`, `NOTION_DATABASE_ID` | Notion 적재를 건너뛰고 콘솔 출력까지만 |
| `SARAMIN_ACCESS_KEY` | 사람인을 건너뛴다 |

```bash
.venv/Scripts/python check_notion.py   # Notion DB 속성이 코드와 맞는지 먼저 확인
.venv/Scripts/python run.py            # 파이프라인 전체
```

Windows 작업 스케줄러에 매일 실행을 등록하려면:

```powershell
powershell -ExecutionPolicy Bypass -File install_schedule.ps1 -At 07:30
```

## 테스트

```bash
.venv/Scripts/python -m pytest tests/ -q
```

테스트는 항상 예시 설정으로 돈다. 개인 설정이 있으면 그 파일의 유효성 검사(스킬 id가 사전에 있는지, 회사 별칭이 겹치지 않는지)가 추가로 돈다.

## 구조

```
collect/    수집기와 공통 레코드(schema.py), 회사 정보 캐시
extract/    직군·경력·지역·규모 판정, 상용구 제거, 스킬·경험 추출
analyze/    스킬 갭, 우선순위
report/     Notion 적재
config/     스킬 사전·판정 규칙·소스 목록, 개인 설정 예시
tests/      계층별 단위 테스트와 파이프라인 조립 테스트
run.py      진입점
```
